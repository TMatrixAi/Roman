## 1. Architecture / data flow

```
API-Tennis (external)
   -> ApiTennisProvider (artifacts/api-server/src/services/tennisData/apiTennisProvider.ts)
      - normalizes raw fields (string/number key coercion, surface/level inference,
        match status, score/margin parsing)
      - TTL-cached (standings 30m, fixtures/matches/h2h 5m) via services/tennisData/cache.ts
   -> TennisDataProvider interface (services/tennisData/types.ts)
      - getTennisDataProvider() factory (services/tennisData/index.ts) returns
        NotConfiguredProvider (clean 502s, no mock data) if API_TENNIS_KEY is unset
   -> Express routes (routes/*.ts) validate with zod schemas from @workspace/api-zod,
      call the provider, and (for predictions) the prediction engine
   -> predictionEngine/index.ts runs 6 modules (surfaceElo, serveReturn, recentForm,
      fatigue, styleMatchup, headToHead) -> ensemble.ts blends 5 of them (weighted by
      reliability) -> calibration.ts shrinks toward 50% by data quality -> upsetRisk.ts /
      recommendation.ts derive user-facing labels
   -> Prediction persisted to Postgres via Drizzle (lib/db/src/schema/predictions.ts),
      engine breakdown stored as JSONB for the detail view
   -> React frontend (artifacts/tennis-predictor) consumes typed hooks generated by
      orval (@workspace/api-client-react) for search, fixtures, matchup builder,
      prediction detail, and the history/ledger page
```

Both api-zod (validation) and api-client-react (React Query hooks) are generated from
`lib/api-spec/openapi.yaml` via `lib/api-spec/orval.config.ts` (`pnpm --filter
@workspace/api-spec run codegen`). Do not hand-edit `generated/` files in either package.

`styleMatchup` is computed and displayed but intentionally **not** fed into the ensemble
(`predictionEngine/index.ts` `moduleEdges`) — it produces qualitative tags/advantages, not
a directly blendable numeric edge. This is a known limitation, not a bug; Phase 6
(specialist models / validated ensemble) is the right place to decide whether/how to
weight it in.

## 2. Bugs found and fixed

1. **Doubles matches misclassified as best-of-5 at Grand Slams.** `determineMatchFormat`
   in `apiTennisProvider.ts` matched on `/atp|men/i` against the provider's
   `event_type_type` (e.g. `"Atp Doubles"`), so men's doubles at a Slam was reported as
   `BestOf5`. Men's doubles is always best-of-3, even at Slams. Fixed by excluding
   `/doubles/i` from the men's-singles check. Verified against live Wimbledon final
   fixtures (doubles now report `BestOf3`, singles unaffected).

2. **Required string query params silently accepted when missing/empty.** The orval zod
   codegen config (`lib/api-spec/orval.config.ts`) coerced query/path strings with
   `zod.coerce.string()`. Zod's coercion calls `String(value)`, so a **missing** required
   param (`undefined`) coerced to the literal string `"undefined"` — 9 characters — which
   passed `.min(2)` and any "required" check. Concretely: `GET /api/players/search`
   with no `query` param returned `200 []` instead of `400`, and `GET /api/h2h` with no
   player ids would have silently queried the provider for a player literally named
   `"undefined"` instead of failing validation. Fixed by removing `'string'` from the
   `coerce.query`/`coerce.param` lists (boolean/number coercion, which is legitimate,
   is untouched) and regenerating `@workspace/api-zod`. Verified: missing/short `query`
   and missing `player1Id`/`player2Id` now correctly return `400`.

3. **Confusing tiebreak scores in match history / H2H.** API-Tennis encodes tiebreak
   sets as decimals (e.g. `"7.7"` vs `"6.5"` for a `7-6(5)` set) instead of separate
   fields. `mapScoreString` was concatenating the raw strings verbatim (e.g.
   `"6.5-7.7"`), which is not a real tennis score and would confuse users. Fixed to
   truncate each side to its whole-games count (`"6-7"`) — honest and readable, though it
   drops the tiebreak point count. (Rounding, tried first, was wrong: `Math.round(7.7)`
   is `8`, which is not a legal game count in a set.) Reconstructing the full `"7-6(5)"`
   notation is deferred until the provider's exact tiebreak-loser-points encoding is
   confirmed (documented inline in `apiTennisProvider.ts`).

4. **`tsc --noEmit` failures in three frontend call sites.** `PlayerSearch.tsx`,
   `PredictBuilder.tsx`, and `PredictionResult.tsx` called the generated React Query
   hooks with `{ query: { enabled: ... } }` but no `queryKey`. The generated hooks'
   declared option type is the real `@tanstack/react-query` `UseQueryOptions`, which
   requires `queryKey` (it's `WithRequired<QueryOptions, 'queryKey'>` upstream) — a gap
   in the orval-generated types, not something specific to this app. Fixed by passing
   the matching exported `getXQueryKey(...)` helper explicitly at each call site (this
   is the same key the hook would have used internally as a default, so behavior is
   unchanged — only the type-check passes now).

5. **Dead code in `serveReturn.ts`.** `ratingsFromMargins` computed two identically-valued
   accumulators (`heldMargin`, `brokeMargin`) from the same loop, then only used one.
   Collapsed into a single `marginSum`. No behavior change (serve and return ratings are
   already documented as the same proxy value, since the provider doesn't expose
   point-level serve/return stats).

6. **Wording bug in risk text.** The orchestrator (`predictionEngine/index.ts`) built the
   risk string `Engine models disagree (${modelAgreement.toLowerCase()})`, which rendered
   `HighDisagreement` as the run-together `highdisagreement`. Fixed to insert a space
   between words before lowercasing, so it now reads "high disagreement".

## 5. Known limitations (not bugs — deferred to later phases)

- **No historical backtesting / calibration corpus.** `calibration.ts` uses a simplified
  data-quality-based shrinkage toward 50% instead of real statistical calibration
  (Brier score / isotonic regression). Phase 3/4.
- **Surface Elo starts every player at a flat 1500 and treats opponents as
  league-average.** No real opponent-strength propagation. Phase 5/6.
- **Serve/return ratings are a game-margin proxy, not real serve statistics** — the
  provider doesn't expose first-serve%, aces, etc. Explicitly labeled as such in the UI.
- **Fatigue reliability is a flat 70, not sample-size-driven** like the other modules.
  Low risk (the underlying match-count signal is real), but worth revisiting if fatigue
  becomes a heavier-weighted signal in Phase 5/6.
- **Surface/tournament-level inference is a static regex table**
  (`services/tennisData/surfaceMap.ts`) covering major tournaments only; smaller
  ITF/Challenger events resolve to `null` surface/level rather than a guess (by design —
  see the file's header comment). Expanding coverage or sourcing it from a second
  provider is Phase 2/5 territory.
- **`API_SPORTS_KEY` and `RAPIDAPI_KEY` secrets exist in the environment but are not
  wired to any provider yet.** Only `API_TENNIS_KEY` (via `ApiTennisProvider`) is active.
  Evaluating a second/fallback data provider is explicitly Phase 2 scope
  ("Validate APIs... harden identity matching"), not addressed here.
- **Player identity matching across endpoints relies on provider-issued `player_key`
  only** — no fuzzy name matching or cross-provider identity resolution. Phase 2 scope.
