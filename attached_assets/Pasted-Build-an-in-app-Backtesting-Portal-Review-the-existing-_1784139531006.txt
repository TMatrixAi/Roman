Build an in-app Backtesting Portal

Review the existing tennis prediction app, Shadow Paper Trading portal, prediction engine, graded-prediction ledger, validation tools, accuracy dashboard, and mobile layout before making changes.

Do not rebuild functionality that already exists. Reuse the existing prediction engine, stored historical datasets, grading logic, model-version system, and visual design wherever possible.

Create a dedicated Backtesting Portal inside the app that works similarly to the existing Shadow Paper Trading system, but is specifically designed for running, reviewing, comparing, and saving historical backtests.

The page must be fully usable on a phone screen.

⸻

Primary goal

Add an in-app page where I can:

* Run historical backtests.
* Select the date range and match groups being tested.
* Choose evaluation-only or training/optimization mode.
* Track active and completed backtest runs.
* Review overall and segmented results.
* Compare the current production model against candidate configurations.
* Inspect correct and incorrect predictions.
* See module-level performance.
* Save, export, rerun, or delete backtests.
* View progress without leaving the app.
* Confirm that a backtest does not silently change the live production model.

The Backtesting Portal must be separate from the Shadow Paper Trading page, but should follow a similar workflow and visual structure.

2. Mobile-first page design

This page must fit correctly on a mobile phone without horizontal scrolling.

Design for a narrow phone viewport first.

Requirements:

* Use a single-column layout on mobile.
* No table should extend past the screen width.
* Convert wide tables into stacked cards on mobile.
* Keep buttons large enough to tap.
* Use compact spacing without making the page crowded.
* Keep text readable without requiring zoom.
* Wrap long tournament names and configuration names.
* Use dropdowns or expandable sections for advanced options.
* Keep the main action buttons visible near the top.
* Use sticky controls only if they do not block content.
* Do not place multiple full-width action buttons side by side when they become too narrow.
* Avoid fixed-width containers.
* Use responsive widths based on the available viewport.
* Test at common phone widths, including approximately 320, 375, 390, and 430 pixels.
* Ensure modals, charts, selectors, cards, and progress panels remain inside the viewport.
* Do not allow charts to overflow the page.
* Charts must resize automatically to the phone width.
* Tooltips and legends must remain readable on mobile.

The mobile design should resemble the Shadow Paper Trading page, but it must be optimized for backtest controls and results.

4. Run New Backtest form

Create a mobile-friendly form for starting a new backtest.

Basic settings

Include:

* Backtest name
* Description or notes
* Start date
* End date
* Model version
* Configuration version
* Dataset version
* Evaluation mode
* Random seed, where applicable

Available modes:

Evaluation Only

* Runs the selected frozen model and configuration.
* Does not modify weights.
* Does not modify thresholds.
* Does not deploy anything.
* Reports historical performance only.

Training and Optimization

* Uses the selected training period to generate candidate weights or thresholds.
* Must use separate validation and holdout periods.
* Creates a candidate configuration.
* Does not automatically replace the production model.

Make the difference between these modes very clear in the interface.

Display a warning before starting Training and Optimization mode:

This process may generate a candidate configuration, but it will not automatically change the live production model.

21. Data integrity and safety requirements

Add protections ensuring:

* A backtest cannot alter stored historical predictions.
* A backtest cannot alter graded outcomes.
* Evaluation mode cannot change weights.
* Training mode creates a separate candidate configuration.
* Production configuration cannot change silently.
* Model versions are stored with every result.
* Future data cannot leak into earlier predictions.
* Post-match data cannot be used as a pre-match feature.
* Cancelled matches and walkovers are excluded appropriately.
* Retirements are reported separately.
* Duplicate predictions are detected.
* The same cohort is used when comparing models.
* Player order cannot reverse the meaning of probabilities.
* Saved probabilities stay attached to stable player IDs.
* Re-running the same deterministic configuration produces the same result.
* Randomized processes record the random seed.
* Deleted backtest runs do not delete original historical prediction records.
